Module A · PI Change Request — System Design

Personal Information Change
Self-Service for Customers

ออกแบบระบบให้ลูกค้าสามารถแจ้งเปลี่ยนข้อมูลส่วนบุคคลได้ด้วยตนเองผ่านลิงค์ที่ Sales / CC ส่งไป โดยไม่ต้องกรอกแบบฟอร์มกระดาษ — ระบบเดิม (POS เมนู 2.8) ยังคงใช้งานได้สำหรับกรณีที่ลูกค้าไม่สะดวกทำเอง

01Why · ปัญหาของกระบวนการเดิม

กระบวนการปัจจุบัน Sales ต้องเป็นคนกรอกข้อมูลแทนลูกค้าทั้งหมด ทำให้เกิดคอขวดและความเสี่ยงด้านการพิมพ์ผิด

กระบวนการเดิม (Sales-Driven)

  • ลูกค้าโทร/มาที่ออฟฟิศ → ขอเปลี่ยนข้อมูล
  • Sales ส่งฟอร์มกระดาษ (PDF) ให้ลูกค้ากรอก + เซ็น
  • ลูกค้าส่งฟอร์ม + สำเนาบัตร กลับมาให้ Sales
  • Sales เปิด POS เมนู 2.8 → กรอกข้อมูลแทน → upload เอกสาร → Submit to REM
  • เสี่ยง: ลายมืออ่านยาก, พิมพ์ผิด, เอกสารหาย, ใช้เวลา 1–3 วัน

กระบวนการใหม่ (Customer Self-Service)

  • Sales/CC คลิก "Generate Link" จากระบบ → ส่งให้ลูกค้าทาง LINE/Email/SMS
  • ลูกค้ายืนยันตัวตนด้วย ID + OTP เบอร์ที่ลงทะเบียน
  • ลูกค้ากรอกข้อมูลใหม่เอง · เห็นข้อมูลปัจจุบัน · เลือกสิ่งที่ต้องการเปลี่ยน
  • ลูกค้าอ่านและยอมรับ PDPA แล้ว Submit
  • ระบบสร้าง PDF ให้อัตโนมัติ + แจ้ง Sales/CC ใน CIRM ให้ตรวจสอบและ Approve → Push เข้า REM

03A1 · Identity Verification — รายละเอียดการตรวจสอบ

หัวใจของระบบ self-service คือการพิสูจน์ตัวตนแบบ 2-factor (สิ่งที่ลูกค้า "รู้" + สิ่งที่ลูกค้า "มี") โดยไม่ต้องสร้างบัญชี

sequenceDiagram
    participant C as Customer (Browser)
    participant W as Web App (CIRM Portal)
    participant API as Identity Service
    participant CRM as Customer Mgmt DB
    participant SMS as SMS Gateway
    participant LOG as Audit Log

    C->>W: เปิดลิงค์ + token
    W->>API: validateToken(token)
    API-->>W: OK · session_id
    C->>W: กรอก ID/Passport + Phone
    W->>API: lookup(id_no, phone)
    API->>CRM: SELECT customer WHERE id_no=? AND phone=?
    CRM-->>API: { customer_id, masked_data, units[] }
    alt Match found
        API->>SMS: sendOTP(phone, ref)
        SMS-->>C: SMS · "Noble OTP 429X4Y · Ref N4F2-9X"
        API->>LOG: write(event=otp_sent)
        API-->>W: { ref, ttl=300s, resend_after=60s }
        W-->>C: หน้า OTP
        C->>W: กรอก OTP 6 หลัก
        W->>API: verifyOTP(session, code)
        alt OTP correct
            API->>LOG: write(event=identity_verified)
            API-->>W: { verified=true, units[] }
            W-->>C: หน้าเลือกห้อง (A1.3)
        else OTP wrong (≤4 ครั้ง)
            API-->>W: { error=invalid, attempts_left }
            W-->>C: ลองใหม่
        else OTP wrong 5 ครั้ง
            API->>LOG: write(event=lockout)
            API-->>W: { locked_until=+30min }
            W-->>C: ปฏิเสธ + ติดต่อ Sales
        end
    else No match in CRM
        API->>LOG: write(event=identity_not_found)
        API-->>W: { error=not_found }
        W-->>C: "ไม่พบข้อมูล · กรุณาติดต่อ Sales"
    end

Validation Rules

เงื่อนไขLogicเหตุผล
Phone ต้องตรงกับ CRMค้น customer ที่ id_no = input AND phone = input (exact match)ป้องกันการสุ่มเลขบัตรแล้วยิง OTP ไปเบอร์ใหม่
OTP ใช้ได้ครั้งเดียว · TTL 5 นาทีเก็บ hash ของ OTP ใน Redis · ลบทิ้งหลังใช้กัน replay attack · ป้องกัน SMS interception
Rate limit · 3 OTP / เบอร์ / ชม.Sliding window 1 ชม.กัน SMS bombing
OTP ผิด 5 ครั้ง = ล็อก 30 นาทีเก็บ counter ใน Redis · TTL 30 นาทีกัน brute-force OTP 6 หลัก
Token ของลิงค์ TTL 24 ชม. · ใช้ได้ 1 ครั้งJWT signed + jti ใน blacklist หลังยืนยันสำเร็จป้องกันลิงค์รั่ว · forward link โดยไม่ตั้งใจ
Lookup เฉพาะลูกค้าที่อยู่ใน CRMJOIN customer × contract WHERE status IN (Completed, Active Rental)ลูกค้าที่ยังไม่จบสัญญา/ไม่ใช่ผู้เช่า ไม่มีสิทธิ์เปลี่ยน — ต้องไป POS
Multi-unit supportSELECT units WHERE owner_id = customer_idลูกค้า 1 คนอาจมีหลายห้อง · เลือก 1 ห้องต่อ 1 คำขอ
ข้อจำกัดที่ต้องระวัง หาก Sales ไม่ได้บันทึกเบอร์ลูกค้าในระบบ CRM (หรือเบอร์ไม่ตรง) ลูกค้าจะ verify ไม่ผ่าน → จึงต้องมี Pre-launch task: ทำ Data Cleansing เบอร์โทร + ID Card ของลูกค้าทุกคนใน CRM ก่อน go-live · หรือเปิดทาง Step-up Verification ผ่าน Sales (Sales เป็นคน trigger OTP จากในระบบ POS)

05Key Design Decisions

  • No Account Requiredลูกค้าไม่ต้องสมัครสมาชิก / ไม่ต้องตั้งรหัส · ใช้ ID + OTP ครั้งต่อครั้ง · ลด friction และไม่ต้องบริหาร password reset
  • Magic Link, Not Open URLลิงค์ผูกกับ token + TTL 24 ชม. · ใช้ได้ 1 ครั้ง · กันไม่ให้ลูกค้าส่งลิงค์ต่อให้คนอื่นโดยไม่ตั้งใจ
  • 2-Factor by DefaultID/Passport (สิ่งที่รู้) + OTP ที่ส่งไปยังเบอร์ที่ลงทะเบียน (สิ่งที่มี) — ระดับความปลอดภัยใกล้เคียงธนาคาร
  • Existing System ยังอยู่POS เมนู 2.8 ยังเปิดอยู่ครบทุกฟีเจอร์ · ใช้กรณี Fallback (ลูกค้าไม่สะดวก / verify ไม่ผ่าน / สูงอายุ)
  • PDF Auto-Generateหลังลูกค้า Submit ระบบสร้างฟอร์ม PDF ภาษาไทย+อังกฤษ พร้อม e-Signature ของลูกค้าและ timestamp · เก็บแทนเอกสารกระดาษเดิม
  • Push เข้า REM ผ่าน API เดิมใช้ endpoint เดียวกับ POS เมนู 2.8 · ไม่ต้องสร้าง integration ใหม่ · REM ไม่รู้ว่าใครเป็นคนกรอก (Customer หรือ Sales)
  • Audit Trail ครบถ้วนทุก event (link generated · OTP sent · verified · field changed · approved · pushed) เก็บลง immutable log · เพื่อ PDPA compliance และ dispute resolution
  • PDPA-Firstแสดงข้อมูลปัจจุบันแบบ masked (ชื่อ ส****ี · เบอร์ 081-XXX-5678) · ขอ Consent ก่อน submit · มีลิงค์ Privacy Policy ทุกหน้า

B

Security Controls

  • HTTPS only · HSTS · TLS 1.3
  • JWT signed (RS256) สำหรับ link token
  • OTP เก็บเป็น bcrypt hash ใน Redis · ไม่เก็บ plain
  • Rate limit ระดับ IP + Phone + ID Number
  • CSRF token + SameSite=Strict cookie
  • WAF rules: blocked common payloads · geo-fence option
  • เอกสารแนบ scan virus + เก็บใน private S3 + signed URL
  • Audit log immutable (append-only) · เก็บอย่างน้อย 7 ปี ตาม PDPA
