01Why · ปัญหาของกระบวนการเดิม

กระบวนการปัจจุบัน Sales/CC ต้องเป็นคนกรอกข้อมูลแทนลูกค้าทั้งหมด ทำให้เกิดคอขวด และไม่รองรับลูกค้าหลายกลุ่ม

กระบวนการเดิม (Sales/CC-Driven)

  • ลูกค้าโทร/มาที่ออฟฟิศ → ขอเปลี่ยนข้อมูล
  • CC ส่งฟอร์มกระดาษ (PDF) ให้ลูกค้ากรอก + เซ็น
  • ลูกค้าส่งฟอร์ม + สำเนาบัตร กลับมาให้ CC
  • CC เปิด POS เมนู 2.6 → กรอกข้อมูลแทน → upload เอกสาร → Submit to REM
  • เอกสารเก็บที่เครื่องของ CC แต่ละคน · ไม่มีระบบรวมศูนย์
  • เสี่ยง: ลายมืออ่านยาก, พิมพ์ผิด, เอกสารหาย, ใช้เวลา 1–3 วัน
  • ไม่รองรับเจ้าของห้องคนล่าสุด (Noble ID Secondary Owner)

กระบวนการใหม่ (Customer Self-Service V2)

  • Sales/CC คลิก "Generate Link" → ส่งให้ลูกค้าทาง LINE/Email/SMS
  • ลูกค้ายืนยันตัวตนด้วย ID/Passport + วันเกิด + OTP (SMS + Email)
  • เลือกห้อง · กรอกข้อมูลใหม่เอง · เห็นข้อมูลเดิม masked
  • ตรวจ PDF ที่ระบบสร้างให้ + วาดลายเซ็นดิจิทัล + PDPA Consent
  • ระบบเก็บข้อมูลรวมศูนย์ใน CIRM · ไม่กระจัดกระจาย
  • Routing email อัตโนมัติ — โครงการเปิดส่งทีมโครงการ · โครงการปิดส่ง App Specialist
  • Push เข้า REM อัตโนมัติหลัง Approve

04Identity Verification · Sequence

2-Factor: ID/Passport + วันเกิด (สิ่งที่รู้) + OTP (สิ่งที่ได้รับทาง 2 ช่องทาง) — ความปลอดภัยใกล้เคียงธนาคาร

sequenceDiagram
    participant C as Customer (Browser)
    participant W as Web App (CIRM Portal)
    participant API as Identity Service
    participant CRM as Customer Mgmt DB
    participant SMS as SMS Gateway
    participant MAIL as Email Service
    participant LOG as Audit Log

    C->>W: เปิดลิงก์ + token
    W->>API: validateToken(token)
    API-->>W: OK · session_id
    C->>W: กรอก ID/Passport + วันเกิด
    W->>API: lookup(id_no, dob)
    API->>CRM: SELECT customer WHERE id_no=? AND dob=?
    CRM-->>API: { customer_id, masked_phone, masked_email, units[], noble_id_member }
    alt Match found
        par Send OTP via 2 channels
            API->>SMS: sendOTP(phone, code, ref)
            SMS-->>C: SMS · "Noble OTP 429X4Y · Ref N4F2"
        and
            API->>MAIL: sendOTP(email, code, ref)
            MAIL-->>C: Email with same OTP
        end
        API->>LOG: write(event=otp_sent_dual)
        API-->>W: { ref, ttl=300s, masked_phone, masked_email }
        W-->>C: หน้า OTP
        C->>W: กรอก OTP 6 หลัก
        W->>API: verifyOTP(session, code)
        alt OTP correct
            API->>LOG: write(event=identity_verified)
            API-->>W: { verified=true, units[], noble_id_member }
            W-->>C: หน้าเลือกห้อง (Step 2)
        else OTP wrong (≤4 ครั้ง)
            API-->>W: { error=invalid, attempts_left }
        else OTP wrong 5 ครั้ง
            API->>LOG: write(event=lockout)
            API-->>W: { locked_until=+30min }
        end
    else No match in CRM
        API->>LOG: write(event=identity_not_found)
        API-->>W: { error=not_found }
        W-->>C: "ไม่พบข้อมูล · ติดต่อ Sales"
    end

05Customer Scenarios · 3 Types

A

Original Buyer

Lookup: CRM contracts WHERE buyer_id = customer_id

  • มีสัญญาซื้อขายโดยตรงกับ Noble
  • เลือกห้อง checkbox อิสระ
  • Select All ทำงาน
  • 1 REQ ต่อ 1 ห้องที่เลือก

Lookup: Noble ID owners WHERE noble_id = customer_id

  • ซื้อต่อจากเจ้าของเดิม ใช้ Noble ID
  • ห้อง preselect + lock
  • Info banner อธิบาย

Foreign Customer

Identifier: Passport + DOB

  • กรอกฟอร์มเป็นภาษาอังกฤษได้
  • Auto-fill TH name จาก EN
  • ที่อยู่ต่างประเทศ → free text
  • Passport + Country of Issue

08Security & Compliance

  • No Account Requiredลูกค้าไม่ต้องสมัคร / ไม่ต้องตั้งรหัส · ใช้ ID + DOB + OTP ครั้งต่อครั้ง · ลด friction
  • Magic Link · TTL 24hJWT signed (RS256) · ใช้ได้ 1 ครั้ง · jti blacklist หลัง verify
  • 2-Factor AuthenticationID/Passport + DOB + OTP via SMS+Email · ตรวจกับ CRM · rate limit + lockout
  • OTP Encryptionเก็บ bcrypt hash ใน Redis · ไม่เก็บ plaintext · TTL 5 นาที · used-once
  • PDPA CompliantMasked data ใน UI · Consent ก่อน submit · Privacy Policy ลิงก์ทุกหน้า · audit log ≥ 7 ปี
  • Cross-mark Documentsลูกค้าต้องขีดคร่อมเอกสารแนบ + ระบุวัตถุประสงค์ → ป้องกันการนำไปใช้ผิด
  • Digital Signature Auditบันทึก signature image (base64) + IP + User Agent + timestamp → หลักฐานทางกฎหมาย
  • PDF Auto-Generateรูปแบบตาม Personal Information Change Form · 2 ภาษา · merge ไฟล์แนบเป็น PDF เดียว
  • REM Push via Existing APIใช้ endpoint เดียวกับ POS เมนู 2.8 เดิม · ไม่ต้องสร้าง integration ใหม่
  • Existing System BackupPOS เมนู 2.6 ยังเปิดอยู่ครบทุกฟีเจอร์ · ใช้ fallback (ลูกค้าไม่สะดวก / verify ไม่ผ่าน)
